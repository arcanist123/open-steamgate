# VS Code for the Web gateway, tree, and webview transport probe

The development and test-web `browser` entry of `editors/vscode/package.json` runs a separate extension in the VS Code web extension host. `npm run vsix:marketplace` removes that entry from its staged package until the web extension is ready for Marketplace distribution. It bundles the prebuilt ABAP gateway and sql.js into one web worker script. The desktop `main` entry remains `extension.js`.

On activation, the web entry imports the preview backend, restores its sql.js database from IndexedDB, starts the gateway, and requests `$metadata`. It does not open an HTTP listener. `osd: Web probe` calls `handleRequest` in that worker: another `$metadata` GET (200), CSRF fetch, a uniquely named `TravelSet` POST (201), and a GET of the created row (200). **OSD Web Probe** output reports both activation start to the activation request's `$metadata` response and probe command start to its own `$metadata` response. `osd: Web verify last Travel` reads that row after a reload.

`osd: Web probe view` opens a webview with a virtual `https://osd.invalid` origin. Its `window.osdBridge.fetch(input, init)` accepts fetch-style URLs and request bodies; `window.osdBridge.installXHR(factory)` is the hook for a later UI5 XHR adapter. The postMessage request carries method, path, query, header pairs, and base64-encoded body bytes. The response carries status, status text, header pairs, and base64-encoded body bytes. The extension accepts only `/sap/opu/odata/` and `/sap/bc/` paths, adds the virtual host and forwarded protocol headers, and returns HTTP-shaped error responses instead of throwing through the message channel. The gateway queue exports every mutation to IndexedDB before its response is sent back to the webview.

The OSD Activity Bar view now has a browser data provider. Its System group shows the in-browser gateway, the serving generation reported by `ZOSD_STATUS_SRV/SystemSet`, and sql.js with IndexedDB persistence. Services come from `ZOSD_STATUS_SRV/ServiceSet` through the same in-worker gateway and are grouped as OData, Apps, ICF, and APC. A single click on a service opens a minimal panel with its name, kind, and URL. The browser entry sets `osd.web`; manifest `when` clauses hide desktop launcher, source, test, and notebook actions while keeping the desktop entry's menus intact. The Activity Bar airship is a 24-pixel monochrome SVG for sharp display at standard and double pixel density.

Every modifying request exports the sql.js database to IndexedDB before the command returns. The stored database is keyed by the preview build ID so a new transpiled generation starts with its own seed. The last probe ID is also stored for the reload check.

## Worker data reads (S2d1)

The worker's `handleRequest` now answers `POST /osd/sql` with the same JSON fields as the desktop SQL door: `sql`, `columns`, `rows`, `count`, and `truncated`. JSON rows retain numbers and nulls. It also answers the desktop client routes `POST /sap/bc/adt/datapreview/freestyle`, `/ddic?ddicEntityName=...`, and `/cds?ddlSourceName=...` with the column-oriented XML consumed by the existing notebook and F8 parsers. DDIC and CDS names must exist as a table or view in the bundled database. The `rowNumber` query parameter sets the requested limit; the default is 100 and the worker ceiling is 1,000. `UP TO n ROWS` is rewritten, and the SQL is bounded before execution even when it already has a limit. Invalid SQL returns HTTP 400 with an error code and message (JSON on `/osd/sql`, XML on ADT routes). The ADT XML format represents cell values as text, as it does on desktop; the JSON door preserves types.

`osd: Web read probe` runs a five-row Open SQL SELECT, a DDIC preview, a capped read, and an invalid statement through the live worker. `npm run web:vscode:test` invokes it in Chromium alongside the existing OData and persistence checks. Editor F8 and notebook UI wiring is the next wave.

## Fiori apps in a webview

`osd: Open Fiori Launchpad` and a click on an **Apps** row of the OSD tree open the launchpad sandbox (`webapp/flp.html`) in a webview tab, at the app's own intent for a row (`ZOSD_STATUS_SRV/ServiceSet` gives an App's path as `/app/flp.html#<intent>`). The apps run against the extension's own in-worker gateway: a row the Travels list report shows, or that a page writes, is in the same sql.js database and the same IndexedDB snapshot as the probes and the other webviews.

`web:vscode` copies the root `webapp/` and the selected packs' pages into `editors/vscode/dist/web/app/`, in the layout the preview gives `build/app/`, plus `packs.json` and `osd-web-apps.json` (each UI5 component's folder and the sandbox's config path). This adds 110 files and 0.49 MiB for core+zork. The extension reads the page and injects a script before anything else in it:

- **XMLHttpRequest** is a subclass of the browser's own. A URL that resolves to `…/sap/opu/odata/…` or `…/sap/bc/…` (relative to the app, or absolute from the resource origin) goes over the postMessage bridge, asynchronously, with readyState, events, headers and `responseType` emulated; every other URL (the UI5 CDN, the app's files) is the browser's own request. `fetch` is wrapped the same way. That covers `../sap/opu/odata/sap/<SRV>/` in the manifests and `../sap/bc/osd/amdp/engine` in `launchpad.js`.
- **Synchronous requests.** Measured with the launchpad and the Travels list report: 17 synchronous requests go to the CDN or the app's files, and they stay native. One goes to the gateway's side: the sandbox's optional `/appconfig/fioriSandboxConfig.json`, a constant (`tools/osd-sandbox-config.mjs`) answered inside the page. No OData request was synchronous. A synchronous gateway request would throw a `NetworkError` and be recorded in `window.osdBridge.stats.bridgedSync`; the test fails on any.
- **Component URLs.** The launchpad's applications point at the BSP path (`../sap/bc/ui5_ui5/sap/<app>/`). A component is loaded by script tags, which cannot cross the message bridge, so before `sandbox.js` runs the page rewrites such a URL to the component's copy under `dist/web/app/`. The data still comes from the gateway.
- **CSP.** `script-src` is a nonce (the page's inline scripts and the bridge), `https://ui5.sap.com` (SAPUI5 core and libraries, as everywhere else) and the webview resource origin (the app's own files). `style-src` adds `'unsafe-inline'` because UI5 renderers write style attributes and the pages carry `<style>` blocks; `img-src` adds `data:` and `blob:` for UI5's icons and theme images; `font-src` and `connect-src` are the CDN and the resource origin. No gateway origin is listed: the gateway is reached by postMessage only.
- **Hash navigation** is the page's own `location.hash` inside the webview frame: tile clicks and in-app navigation work as in a browser.

### Launchpad tiles

The launchpad opens a tile that is not a UI5 component (Zork, WEBGUI, System information, Data browser, Vivid Vibes, LSD, Source) in a new browser window, on GitHub Pages as well. A webview can neither open a window nor navigate, so the page's runtime routes what a browser would do with an address:

- **Gateway pages.** `window.open`, a link click and a form submit to a `/sap/bc/` path go to the extension, which asks the gateway for the page (following redirects) and renders it in a webview panel: a new panel for a new window, the same panel for a link or a form. The page gets the same policy, base URL and runtime as a Fiori page; its own scripts get the nonce. Clicks are taken in the capture phase, because UI5 stops the click of its own controls before it reaches the window, and they are stopped before VS Code's webview link handler, which acts on any `<a>` regardless of `defaultPrevented`: without that, a tile opened the bare webview host page in a browser window next to its target.
- **Script-less sandboxed frames.** The WEBGUI draws a transaction's HTML viewer in a `srcdoc` frame with `sandbox="allow-forms …"` and no `allow-scripts`. Such a frame gets `allow-same-origin` when the page is rendered, so the runtime can route its forms from outside; nothing can run inside it either way. The rewrite is fail-safe: a frame is touched only when its whole tag parses under a strict grammar (names `[a-zA-Z-]+`, values double-quoted, valueless names, no name twice), it has `srcdoc` and no `src`, and its `sandbox` value is ASCII letters, `-` and spaces only, so no character reference can spell a token, with neither `allow-scripts` nor `allow-same-origin` among the lower-cased tokens. Any other frame, odd markup included, keeps its tag as written (`sandboxScriptlessFrames` in `editors/vscode/web/page-host.mjs`). Each frame is hooked once, and the page's observer works on a changed `src` or `style` of its own element only; an added subtree is scanned once. (On GitHub Pages the same form posts to an origin-absolute path and gets GitHub's 405.)
- **App pages and outside addresses.** An address under `/app/` opens as a Fiori page in its own panel; any other `http(s)` address goes to `vscode.env.openExternal` (the Source tile and the QR tile beside it).
- **APC.** A `WebSocket` to `/sap/bc/apc/…` is a stand-in that talks to the extension over the same message channel; the extension drives the channel's ABAP handler through `openChannel`, `channelMessage` and `closeChannel` of `web/preview-backend.mjs`, as the preview's service worker does. A channel belongs to one document. The extension names each document when it assigns the panel's HTML (a random id, in the same synchronous step, so before the page runs), and the page sends that name with every `apc-open`, `apc-send` and `apc-close`; a message with any other name is ignored. New HTML or a closed panel ends the old document at once: it can register no channel and reach the page no more, and its channels are closed afterwards. Channels are keyed `<doc>:<socket>` (socket ids carry a random name of the runtime's run, so a reload never reuses one, and a reused id is refused with 1008); an open re-checks after every await that its document is current and its key still its own, and closes only what it opened, through the backend entry it got from `channelHandle` (`closeChannel(id, handle)` in `web/preview-backend.mjs` leaves a different entry under the same id alone; without a handle it behaves as before, which is what the Pages service worker calls). `pageChannels`, `test/vscode-web-page-host.mjs`.
- **Gateway media.** An `<img>`, `<audio>`, `<video>` or `<source>` whose `src` is a gateway path, set by a script or by markup, and a `background-image` with such a URL (how `sap.m.Avatar` shows the `PhotoSet` pictures in the Travels list), is fetched over the bridge and given a `blob:` URL; `play()` waits for it. A failed load is not kept. Past 16 cached blobs, one is revoked only when the live document provably no longer uses it: no element of the document or of a same-origin frame names it in `src`, `currentSrc`, `poster`, `srcset`, a `style` attribute or its inline background, no `<style>` text holds it, no element still waits for its path, and no media element outside the document plays it (`mediaUrlsInUse` in `page-host.mjs`); when in doubt it is kept. The tile test checks the bound (40 distinct pictures in the Travels page), that a blob URL copied to another `<img>` and to a background survives while they show it, that 20 retained elements whose backgrounds were cleared release their blobs, and that the demos' music loads and plays.
- **SMW0 media.** `web:vscode` copies the transpiled W3MI files (the Zork story file, the demos' pictures and music) to `dist/web/media/`, and the web entry's W3MI loader reads them from the extension's own files. VS Code's file reads in the browser lose a `%` in a name, so `@` is the escape character instead: `@` is stored as `@40` and `%` as `@25` (`mediaFileName`), which keeps two names from sharing a file.
- **Greyed tiles.** The launchpad greys the Workbench unless `HEAD /sap/bc/adt/core/discovery` answers 200. The worker answers it, but the Workbench needs the Node host's ADT continuations and reports "ADT discovery failed: HTTP 404", so the launchpad's question is answered with 404 in the page and the tile is grey, as on Pages. The AMDP sandbox is grey because sql.js has no SQLScript engine; on the main Pages deployment it is live on DuckDB-Wasm.

Vivid Vibes and LSD need the `o4d` and `lsd` packs (`OSD_WEB_PACKS=all`); the default core+zork build still shows their tiles, and they open the gateway's 404 page there.

Not covered yet: a webview restored after a reload (the tab closes and is opened again from the tree or the command); `url()` in style sheets (only inline `background-image` is rewritten); `location.href = …` navigation from a page's script; binary WebSocket frames.

`npm run web:vscode:test` opens the launchpad through the command palette and checks four tile texts, clicks the Travels tile and waits for row `T0001`, writes a TravelSet row through the page's own `fetch`, presses Go and waits for that row, reads it from the probe view, reloads VS Code, clicks the `stg.travel` row under Apps and waits for the same row. It saves `fiori-launchpad.png`, `fiori-travels.png`, `fiori-travels-created.png` and `fiori-tree-app.png` under `$OUT_DIR` (default `/tmp/osd-shots`).

It then clicks every tile in turn (`scripts/test-web-tiles.mjs`) and asserts what the GitHub Pages preview shows for it: the seven UI5 apps' rows (Travels with its `PhotoSet` pictures decoded from `blob:` URLs), the Workbench and AMDP tiles greyed, Zork answering `open mailbox`, the WEBGUI running `ZOSD_NOTE` from the command field and adding a notepad line through the viewer frame's form, System information, the Data browser's rows of `ZC_STG_TRAVEL`, Vivid Vibes and LSD playing over their push channels (when their packs are built), and Source and the QR tile opening exactly one browser window at the repository. Each saves `tile-<name>.png`.

## DuckDB-Wasm (`osd.web.database`)

The setting `osd.web.database` chooses the in-browser gateway's engine: `sql.js` (default; the database is kept in IndexedDB across reloads) or `duckdb`, the engine of the GitHub Pages main preview. One bundle serves both: the extension tells `web/preview-backend.mjs` the engine and the binary's address before importing it (`globalThis.__stgPreviewHost`), and `test/setup.mjs` opens `DuckDBWasmClient` there. `web:vscode` copies `duckdb-mvp.wasm` (39,362,651 bytes) into `dist/web/` beside `extension.js`, not into it; the extension fetches it from its own location only when the setting says `duckdb` (an `http(s)` location directly after a HEAD check, any other scheme through `workspace.fs` and a blob URL). A missing file is an activation error that names it. `extension.js` did not grow: the DuckDB-Wasm JavaScript was already in it.

On DuckDB the database lives in memory and is reseeded on every reload: nothing is written to IndexedDB, the tree reads **Database: DuckDB-Wasm (in memory, reseeded on reload)** and the status bar says so after activation. A changed setting asks for a window reload (**Reload Window**); the worker holds one ABAP runtime and one connection, and the engine is not swapped under it.

What DuckDB adds here is Portable AMDP. A SQLScript notebook cell runs on it: the worker answers `POST /sap/bc/osd/amdp/cell` with `portableCell` over the gateway's own connection, the same way the Node host does (`mountPortableCells`), and the cell shows **Portable AMDP (limited) on duckdb**. On sql.js the cell still says it is not available in the browser. The launchpad's **AMDP sandbox** tile is grey on DuckDB, exactly as on the Pages main preview (recorded there on 2026-10-22): "needs a database that speaks it", "no SQLScript engine here", and `/sap/bc/osd/amdp/engine` answers `{"engine":"none","destination":"AMDP","system_db":"duckdb"}`. The sandbox page runs bodies on HANA only on every host; Portable AMDP compiles class methods and notebook cells, not the sandbox.

`OSD_WEB_TEST_DB=duckdb npm run web:vscode:test` runs the sql.js probe and read probe, then `scripts/test-web-duckdb.mjs`: it writes the setting in the user settings JSON, presses **Reload Window** on the extension's prompt, runs the probe on DuckDB, checks the tree label, opens the launchpad and checks the AMDP tile and `/engine`, and runs the SQLScript cell of `examples/abap-amdp.osdnb` (ANSWER 42). Screenshots: `duckdb-setting-prompt.png`, `duckdb-tree.png`, `duckdb-launchpad-amdp.png`, `duckdb-sqlscript-cell.png`. Measured on 2026-10-22, activation to first `$metadata`: sql.js 1.6-2.7 s, DuckDB 4.7-8.5 s in `@vscode/test-web`, 5.1 s in vscode.dev with the binary from `https://localhost`.

## Scope and limits

This S2c wave proves the transport contract and a thin webview write path. The service panel shows only name, kind, and URL; it has no source links or entity sets. APC push channels are bridged for pages in webviews only (see "Launchpad tiles"). The desktop extension's Test Explorer, launcher, notebooks, and other Node-backed commands are not implemented in the web entry. Stored databases are not migrated between gateway build IDs. Packaging a published web VSIX and tests in browsers other than Chromium are outside this probe.
